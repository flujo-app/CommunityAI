## First supported shape

Use one independent, explicitly pinned worker process per selected GPU, with distinct worker identities and intentional block ranges. Do not begin by enabling tensor parallelism for Qwen or removing the single automatic-worker restriction. The current configuration already accepts explicit worker devices; launch and supervision have per-device VRAM reservation fields. This is a product integration and resource-contract gap, rather than an entirely absent runtime capability.

The following source survey describes the baseline before this branch's first patch; its listed line numbers refer to that baseline. Canonical launch pinning, bounded inventory, worker status, pool validation and UUID-based power monitoring are implemented in the current patch. Physical selection persistence, live identity/loss gates for uncapped workers, desktop controls and profile isolation remain open.

Concrete baseline support and gaps:

- `src/drift/node/config.py:445` permits `WorkerConfig.device`, but `:647` restricts `model == "auto"` to one worker. Automatic planners would otherwise plan against overlapping coverage; simply deleting the restriction can duplicate placements. Keep this restriction for the first volunteer build and select explicit, nonoverlapping block ranges.
- `src/drift/cli/run_node.py:610` resolves each worker's device and calculates a VRAM allowance for it, but `:685` emits `--device` only when the original setting was explicit. Always pass the resolved canonical device so the device reserved by the supervisor matches the device used by the child.
- `src/drift/node/worker_supervisor.py:438` sums reservations among workers on the same `vram_device`. Preserve this behavior. `tests/test_worker_supervisor.py:637` already tests same-device contention; extend it with independent-device reservations, mismatched capacities and device loss.
- `src/drift/node/hardware_status.py:38` and `desktop/src/communityai_desktop/client.py:420` expose a singular GPU. `desktop/src/communityai_desktop/controller.py:196` and `desktop/src/communityai_desktop/pyside_shell.py:841` display one card and one VRAM budget. Add a bounded per-device inventory, worker-to-device status, and explicit per-device opt-in before presenting multi-GPU controls. `src/drift/node/server.py:121` projects the allowance but omits the worker's device identity.
- `src/drift/server/processing_budget.py` deliberately shares a compute/cooldown lock across workers when the processing percentage is below 100. It serializes different GPUs too. Keep the existing node-wide meaning until a separately named, tested per-device scope exists; do not silently multiply the user's requested processing budget.
- `src/drift/node/worker_supervisor.py:124` uses an NVML device index for power monitoring, supplied from the CUDA ordinal at `src/drift/cli/run_node.py:748`. A CUDA-visible ordinal is not a reliable NVML physical index when `CUDA_VISIBLE_DEVICES` reorders devices. Resolve stable device identity for monitoring, or explicitly refuse power-capped launch when mapping cannot be established. `tests/test_node_config.py:1281` already tests two mocked ordinal-scoped monitors; it does not test CUDA/NVML physical mapping.
- `src/drift/node/local_inference.py` prefers `cuda:0` for fallback. Account for contention with sharing workers; the volunteer default should use CPU fallback or an explicitly excluded device until shared accounting is implemented.

## Smallest first patch

First patch scope: `src/drift/cli/run_node.py`, `src/drift/node/hardware_status.py`, `src/drift/node/worker_supervisor.py`, `src/drift/node/server.py` and their four corresponding test files. Add backward-compatible per-device inventory and worker device status; pass a resolved indexed device on every GPU worker launch. Bound the inventory at 16 supported visible devices and return an explicit unsupported/excess-device status instead of silently selecting another card. Preserve the singular legacy fields for existing desktop clients. Keep one automatic worker and existing percentage semantics. Verify missing or invalid selected devices fail visibly without moving work onto another GPU. Same-device workers must agree on the pool size; separate device pools remain independent. CUDA power monitoring resolves private Torch UUIDs to NVML handles without using visibility-relative indices as physical indices. This patch can be tested locally with injected two-device inventory and one real GPU; it does not establish physical multi-GPU operation. No desktop changes, automatic placement expansion or tensor-parallel changes belong in this first patch.

The new list exposes saved per-device policy capacity, not selected/enabled cards, live free VRAM or summed host capacity. Legacy singular values alias one list entry and must not be added again. Existing desktop clients ignore the added fields and still display one GPU. Invalid saved selections currently cause a worker-specific configuration error during node startup, even if sharing is off; graceful per-worker recovery is a later product requirement. A canonical ordinal is not a persisted physical identity. The private power binding protects only power-capped CUDA workers within the current node lifetime; uncapped workers, restart/reordering, and XPU device-loss handling still require the next identity phase before any volunteer artifact.

Then execute these bounded patches in order:

1. **Device identity and resource scope:** `src/drift/utils/hardware.py`, `src/drift/cli/run_node.py`, `src/drift/node/worker_supervisor.py`, `src/drift/node/config.py`, and their existing tests. Resolve a selected physical GPU to its visible CUDA ordinal and NVML UUID/PCI mapping locally; do not publish unique hardware identifiers. Reject changed/missing mappings until the user reselects the card. Add an explicit processing scope (`node`, legacy default; `device`, new opt-in) in `config.py`, `run_node.py`, and `server/processing_budget.py`. Derive per-device lock paths from a stable local mapping, keeping same-device workers serialized. Keep existing `test_shared_workers_cannot_overlap_compute_or_cooldown`; add same-device and different-device concurrency tests. Do not change global semantics silently.
2. **Selection and controls:** `src/drift/node/config.py`, `desktop/src/communityai_desktop/client.py`, `controller.py`, `pyside_shell.py`; extend `desktop/tests/test_client.py`, `test_resource_controls.py`, and `test_resource_playthrough.py`. Display one enable switch and memory allowance per device, the resolved worker/device association, and processing/power scope. Write explicit workers with unique identity files, unique bound ports, pinned devices and chosen nonoverlapping block ranges. Use the existing node's revision-bound control/config-write path rather than a competing desktop file writer. One shared verified cache may avoid duplicate downloads, but account unique artifacts and aggregate disk use once for the node.
3. **Isolated volunteer profile and build:** the desktop files listed below, `desktop/tests/test_lifecycle.py`, `test_credentials.py`, `test_startup.py`, `test_maintenance.py`, `test_simple_desktop.py`, and `test_build_desktop.py`. Prove the test app can start, stop and be removed alongside the regular app without sharing its credentials, instance lock, updater or node directory. Integrate reviewed main safety fixes and relevant reviewed runtime fixes before qualification.

Defer multi-device automatic placement until it can allocate the node's coverage, artifact budget and per-GPU footprints together. The existing planners are per worker and do not establish that joint contract. Tensor parallelism is also separate: `server/backend.py:111` rejects tensor-parallel recurrent caching, and paged cache is single-device at `:165`. The first implementation must not promise that a Qwen recurrent block spans GPUs.

## Safe default and acceptance contract

Sharing starts off, with no automatic login startup, automatic update, or model download for the volunteer profile. The user selects each GPU separately and sees its total VRAM, selected allowance, actual worker device and observed usage. The initial proposed contract is:

| Resource | Default and enforcement contract |
| --- | --- |
| Device selection | No card enabled initially. Enable one first; a second is a separate explicit action. An absent/renumbered card never sends its worker onto another card. |
| GPU memory | Suggest at most 50% of that card's total, additionally leaving at least 1 GiB of currently free VRAM outside the proposed allowance. If the result or the measured model/block footprint is insufficient, refuse that placement; never silently raise the budget. The same-device sum of worker reservations cannot exceed the selected device allowance. The exact eligible footprint is determined from volunteer inventory and existing model evidence. |
| Processing | Default 50% with the existing node-wide scope, clearly labeled. Concurrent capped GPU operation requires explicit per-device scope and its tests; 50% on two GPUs must not be presented as the original single global 50% promise. |
| Power | No invented wattage default. An optional limit is labeled **per selected GPU**, matching current supervisor behavior. A requested aggregate host/node power cap remains unsupported until there is aggregate measurement and enforcement. Missing mapped telemetry with a configured limit prevents launch. This is sampled admission/pause behavior, not a hardware power-limit command. |
| Host RAM, cache and bandwidth | Compute a combined worker/loading estimate and require available host headroom before enabling the second GPU. Establish a finite node disk ceiling and a volunteer-chosen finite bandwidth limit before model downloads; do not give every worker an independent copy of the node allowance. No hard host-RAM limit is claimed by the current configuration. If these aggregate checks cannot be established, remain in single-worker mode. |
| Local fallback | Use CPU with its own finite admission budget, or disable it; do not automatically load fallback onto a GPU already reserved for sharing. |
| Stop and restart | Pause Sharing cancels every managed worker and releases every reservation. Exit must leave no child processes. Restart preserves chosen limits but does not resume volunteer sharing automatically. |

The memory suggestion is a conservative starting policy, not a guarantee against allocation failure or interference by other applications. PyTorch allocator fractions and reservation accounting do not cover every driver or third-party allocation; do not call this a driver-enforced whole-device memory ceiling.

Local acceptance: test two simulated devices, unequal VRAM, canonical launch arguments, same-device reservation rejection, independent-device reservations, missing-device failure, `CUDA_VISIBLE_DEVICES` reordering, legacy global processing locks, new per-device locks, GUI selection and global stop. Verify loopback control credentials and test profile isolation. Run a real single-GPU worker with existing model artifacts if available; do not download weights or install dependencies under this planning task. Existing focused entry points are `tests/test_node_config.py`, `test_node_hardware_status.py`, `test_worker_supervisor.py`, `test_processing_budget.py`, and the named desktop tests. Record the interpreter/environment used rather than assuming the isolated worktree has a working runtime. Simulations cannot prove simultaneous physical GPU execution, multi-GPU throughput, thermal behavior or actual device-loss handling.

Volunteer acceptance: first enable one GPU, then two. Verify workers are bound to the selected physical GPUs, per-device memory remains within the documented contract, generation succeeds, cancellation works and stopping leaves no workers. Test simultaneous utilization with independent requests or another workload that can exercise both workers; a single autoregressive request across sequential block spans does not imply simultaneous use or twice the speed. Exercise an unavailable selected GPU through configuration or a controlled restart, never by physically removing a live card. No fallback onto another card is acceptable. Compare one versus two GPU measurements with the same model, prompt length, output length and backend; record load time, time to first token, tokens/second, request concurrency and peak per-device memory, without promising a speedup. Run a bounded ten-minute generation/stop/restart check if the volunteer agrees. Retain sanitized version, GPU model/count, budget, timing and failure information; do not ask for keys, raw prompts or public hardware identifiers.

## Future build and install workflow

The first volunteer artifact should be a clearly labeled portable test build with an isolated data directory, API port, credential service/account, instance lock, update cache and startup identity. A different branch or Windows installer AppId alone is insufficient. `desktop/src/communityai_desktop/app.py` accepts several profile paths, but does not pass a separate shell instance name. `pyside_shell.py:1264`, `startup.py:14`, and `maintenance.py:15` still use CommunityAI defaults. The normal update feed is hardcoded in `updater.py`; test builds must not consume it. `desktop/installers/communityai.iss:24` uses the normal installation directory even with a custom AppId. Review and patch all profile identities before issuing any archive, installer or launcher. The ordinary Linux package identity must likewise not replace the installed package.

Use `desktop/build_desktop.py` with a unique volunteer version in `desktop/src/communityai_desktop/release.py`, separate `--output-root`/`--build-root`, the verified `--publication-bundle`, and a committed reviewed `--source-commit`. Its runtime qualification (including its pinned torch build), self-tests, release metadata, source provenance and SHA256 output remain required. Confirm disk headroom locally. A source-only check or another branch's binary is not the qualified volunteer artifact. Unsigned engineering bundles must retain their existing unsigned labeling; checksums do not establish publisher signing. Prefer an isolated portable archive over the ordinary Windows installer or Linux package until side-by-side isolation is proven. Building and publication are future steps, not actions taken in this survey.

The eventual volunteer-facing instructions should be short and require no hand-edited JSON:

1. Download the specifically linked **CommunityAI Multi-GPU Test** archive for your OS and verify the displayed checksum.
2. Extract it into its own folder and launch the test application. Confirm its version label; the regular installation stays in its own profile.
3. Select one GPU, review the shown memory/processing limits and model download size, then enable sharing. Wait for the worker to become ready.
4. Select the second GPU only after the first succeeds, run the supplied non-sensitive sample request and inspect both device statuses. Send the sanitized diagnostic summary if a worker fails.
5. Select **Pause Sharing**, wait until every worker shows stopped, then **Exit**. Remove only the test profile and extracted folder after stopping if you no longer want the test build.

Final exact labels, archive filename and steps must come from the tested build, not this proposal. Do not send a build until reviewed safety fixes are integrated, profile isolation is verified locally and the volunteer's hardware matches the qualified runtime. Do not report multi-GPU acceptance until real two-device results exist. Current delivery is source implementation and local validation, not a qualified volunteer build; spending is **$0**.
