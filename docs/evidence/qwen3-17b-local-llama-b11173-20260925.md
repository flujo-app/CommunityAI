# Real local llama.cpp CUDA smoke — September 25, 2026

Status: **passed for one RTX 2070 SUPER and cached Qwen3-1.7B**, including
the typed provider adapter, authenticated CommunityAI API seam and owned local
process. The installed desktop route, multi-GPU qualification and the requested
DeepSeek/GLM models remain separate release gates.

The pinned upstream `ggml-org/llama.cpp` release is `b11173`, source commit
`84e76d8a23162eca70490da131945ebec1f09bf4`. The Windows CUDA 12.4 binary
archive (254,719,399 bytes) matched SHA-256
`322a376be0ebecdf965d3519a8cc9f5b318ea1f8766f5e2a955877f60339900c`.
The CUDA runtime archive (391,443,627 bytes) matched
`8c79a9b226de4b3cacfd1f83d24f962d0773be79f1e7b75c6af4ded7e32ae1d6`.
`scripts/prepare_llama_b11173_local.py` verified both before extracting their
55 files. The extracted `llama-server.exe` identified build 11173 and commit
`84e76d8a2`; its SHA-256 is
`925ea12e72149baba11041f77394b6e07951eac6693118762db882b78687172e`.

The source converter accepted the complete existing local
`Qwen/Qwen3-1.7B` snapshot at revision
`70d244cc86ccca08cf5af4e1e306ecf908b1ad5e` in an offline dry run. The
bounded F16 export then completed in about 70 seconds. Its GGUF is 4,069,678,976
bytes, SHA-256
`11612b8bbfbbe59d484541a6bcda2a8d84632600fdfbe00d2290c726bb6cbf7d`.
No remote weights or model bundle were downloaded.

`scripts/smoke_llama_b11173_local.py` started one contained process on
`127.0.0.1`, with a temporary API-key file, UI/slot endpoints disabled,
`CUDA0`, all GPU layers, one slot, 256-token context, prompt cache disabled,
and offline Hub flags. It sent one four-token warmup and three 16-token
OpenAI-compatible completions using the same six-token prompt as the local
Transformers reference. It also consumed one bounded streaming completion.
The final run returned nonempty text and exact usage for every measured request:

| Request | Client wall time | Server reported total time |
| --- | ---: | ---: |
| 4-token warmup | 0.062 s | 0.061 s |
| 16-token 1 | 0.188 s | 0.182 s |
| 16-token 2 | 0.859 s | 0.181 s |
| 16-token 3 | 0.172 s | 0.182 s |

The measured client median is **0.188 seconds for 16 tokens** in this recorded
run; a later API integration run measured 0.203 seconds. The second
client request had a repeatable ~0.9-second wall-time outlier across runs,
while the server's reported compute time stayed near 0.2 seconds; its cause is
unproven. The verbose server log explicitly reports **29/29 layers offloaded to
CUDA0**, a 3,281.97 MiB CUDA model buffer, and a 28 MiB CUDA KV buffer. Local
GPU used memory increased by 3,425 MiB while loaded. The streaming endpoint
sent five JSON frames followed by `[DONE]`, retained the configured model alias,
ended with `finish_reason=length`, and supplied a final usage object. The owned process tree
was confirmed stopped, no `llama-server.exe` remained, and GPU used memory
returned near the prior level.

The follow-up standalone checks established a bounded CommunityAI path:

- `scripts/check_managed_llama_cpp.py` passed fake-SSE identity, usage,
  authentication, text-bridge admission and quarantine checks in under a second.
- `scripts/check_managed_llama_cpp_api.py` passed a fake-backend request through
  CommunityAI's authenticated `/v1/completions` route and rejected an output
  limit that would exceed the 256-token local context. The existing managed
  vLLM adapter and API checks also passed after this bridge change.
- A later `scripts/smoke_llama_b11173_local.py` run passed the typed adapter and
  CommunityAI API against the **real** pinned llama.cpp server. It returned
  nonempty text and exact usage, and `/props` reported build
  `b11173-84e76d8a2`. Its three 16-token requests had a 0.203-second client
  median; one client wall-time outlier recurred while server compute stayed
  close to 0.2 seconds.
- `scripts/check_managed_llama_cpp_process.py` exercised
  `ManagedLlamaCppProcessOwner` against the same real binary and GGUF. A wrong
  GGUF hash prevented launch. A matching process owned its loopback listener,
  exposed one exact model and 256-token context, produced an accepted typed
  completion, and stopped its entire contained process tree on cancelled
  streaming. No server remained afterward.

The owner currently admits only **one** CUDA device and synthetic `test/*`
profiles. It verifies pinned executable and GGUF hashes before launch, confines
the HTTP listener to loopback, holds the API key in a temporary file, uses a
bounded metadata probe, and requires live process/listener ownership before
dispatch. These checks are part of source, but an installed product route and
production model qualification are still pending.

The [same-device Transformers baseline](qwen3-17b-local-transformers-baseline-20260925.md)
had a 0.672-second median with the same model revision, F16, prompt and output
length. The two scripts use different execution/API paths, so this is a
directional local comparison, not a controlled release-wide speed claim.
Concurrency, long contexts, quality, useful multi-GPU, installed product paths,
and the exact DeepSeek and GLM models remain untested. The large pinned vLLM
image did not finish downloading within separate three- and ten-minute caps;
this llama.cpp result does not establish vLLM execution.
